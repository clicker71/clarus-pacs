# Clarus Bridge — DIMSE to DICOMweb Adapter

**Python + pynetdicom. Translates ancient DIMSE into modern DICOMweb.**

[![License: LGPLv3](https://img.shields.io/badge/license-LGPLv3-blue)](../LICENSE)
[![Bridge CI](https://github.com/clarus-pacs/clarus/actions/workflows/bridge-ci.yml/badge.svg)](https://github.com/clarus-pacs/clarus/actions/workflows/bridge-ci.yml)

> [!] **DEVELOPMENT RULE:** Never edit `clarus-bridge.py` directly.
> It is auto-generated by `bundle.py` from `clean_code/` modules.
> Always edit files in `clean_code/`, then run:
> ```bash
> python bundle.py
> ```

## What It Does

Your 2004 CT scanner speaks `C-STORE`, `C-FIND`, `C-MOVE` over TCP port 104. A DICOMweb origin server speaks `STOW`, `QIDO`, `WADO` over HTTP (Clarus by default; any DICOMweb-compatible server works). The bridge sits in the middle and translates:

```
Old Modality --C-STORE/C-FIND--> Bridge (:8104) --STOW/QIDO--> DICOMweb origin server (e.g. Clarus :8024)
              pynetdicom AE                                  Clarus (Rust, B-tree storage)
```

| DIMSE Service | DICOMweb Equivalent | Status |
|:---|:---|:---:|
| C-ECHO | Verification | OK |
| C-STORE | STOW-RS | OK |
| C-FIND (Patient/Study/MWL) | QIDO-RS / UPS-RS | OK |
| C-MOVE | WADO-RS + C-STORE forwarding | OK |
| N-ACTION | Storage Commitment Push | OK |
| C-PRINT | DICOM Print (PS3.4 §H) | OK Generic driver. Vendor-specific: **[Help Wanted!](../README.md#c-print-film-printing)** |
| C-GET | — | rejected (use C-MOVE) |

## How It's Built

Bridge development uses a **Clean Architecture** multi-module structure (`clean_code/` package — 18 files, ~3400 lines). For distribution, `bundle.py` assembles everything into a single `clarus-bridge.py` — zero build tools, zero config, just one file.

```
Development:                  Distribution:
clean_code/                   clarus-bridge.py  ← pip install + wget, run
├── handlers/           bundle
├── db.py               ────►  (single file,
├── utils.py                  ~3400 lines)
├── http_server.py
└── ...                       User never sees
(17 modules,                  the modules.
 45 tests)                
```

**For contributors:** see `clean_code/` — each DIMSE service is isolated, tests are per-module, Pylance is clean.  
**For users:** download `clarus-bridge.py` + `sop_classes.yaml` — that's it.

Full developer docs: [docs/bridge.md](../docs/bridge.md).

## Quick Start

**Basic setup — 2 files, C-STORE/C-FIND/C-MOVE/N-ACTION ready:**

```bash
pip install -r clbridge/requirements.txt

wget https://github.com/clarus-pacs/clarus/releases/latest/download/clarus-bridge-linux-amd64.tar.gz
tar xzf clarus-bridge-linux-amd64.tar.gz

# Edit clarus-bridge.conf, then:
python clarus-bridge.py
```

> Without `sop_classes.yaml`, Bridge falls back to 11 built-in SOP classes (8 active + 3 retired).
> For custom modalities, edit the YAML file and restart.

Then configure your modality to send to AE Title `CLBRIDGE` at `your-host:8104`.

**Production setup (persistent state, survives restarts):**

```bash
# Edit clarus-bridge.conf:
#   [server] port = 104
#   [dimse] scp_default_port = 104
python clarus-bridge.py --config /etc/clarus-bridge.conf
```

**OOM Protection:** Bridge uses an in-memory queue. A background Health Checker monitors the configured DICOMweb origin server every 5s; if the server is unreachable for >30s, C-STORE returns `0xA700` (Out of Resources). Graduated backpressure warns at 60% fill, rejects at 80% (`0xA700`), and hard-rejects at 95% (`0xC000`). Worker count and queue budget auto-size from system RAM — no manual tuning needed.

| `[advanced]` key | Default | Purpose |
|:---|---|:---|
| `stow_queue_max_mb` | `0` (auto = 15% RAM) | Max RAM for queue. Replaces the old slot-count limit. |
| `stow_workers` | `0` (auto = cpu_count/2) | Background STOW-RS worker threads. |
| `stow_queue_size` | `5000` | Max pending requests (slot count; use `stow_queue_max_mb` for byte-based sizing). |

**C-MOVE works automatically:** Bridge auto-registers any peer that sends C-ECHO or C-STORE
as a valid move destination. Use `--peer` only for destinations that never initiate connections
(e.g., a PACS archive on a different subnet).

> ⚠️ **C-MOVE + restart = lost index.** By default, Bridge keeps SOP mappings in memory
> (`:memory:`). After a restart, it forgets which instances it already sent, and a
> repeated C-MOVE may re-send everything. For persistent tracking, always add:
> ```bash
> # Add to clarus-bridge.conf: sop_index_db = /var/lib/clarus/bridge-index.db
python clarus-bridge.py --config /etc/clarus-bridge.conf
> ```

### Optional: Prometheus /metrics

```bash
pip install prometheus_client psutil
# GET /metrics and GET /health become available on the [metrics] health_port (default 8105)
```

If `prometheus_client` is not installed, `/metrics` returns 503 — bridge core works fine without it.
If `drivers/` folder is not present, C-PRINT is disabled — bridge core works fine without it.

> **Note:** `/metrics` returns `Content-Type: text/plain; version=0.0.4` — this is the
> [Prometheus OpenMetrics exposition format](https://github.com/prometheus/OpenMetrics) version,
> **NOT** the bridge version. Bridge version is reported by `--version` (`0.3.0-alpha`).

## Configuration Reference

Bridge uses a single `clarus-bridge.conf` file (nginx-style). All settings go here — no CLI flags except `--config` and `--version`.

Default config: [clarus-bridge.conf](clarus-bridge.conf)

| Section | Key | Default | Description |
|:---|:---|:---|:---|
| `[server]` | `host` | `127.0.0.1` | DIMSE listen address |
| `[server]` | `port` | `8104` | DIMSE listen port. Use `104` for production DICOM. |
| `[server]` | `ae_title` | `CLBRIDGE` | DIMSE Application Entity title |
| `[dicomweb]` | `clarus_url` | `http://127.0.0.1:8024/dicomweb` | Full DICOMweb base URL of the origin server to forward to (any DICOMweb-compatible server) |
| `[dimse]` | `c_find_max_responses` | `500` | Max C-FIND results per query |
| `[dimse]` | `scp_default_port` | `104` | C-MOVE SCP destination port |
| `[logging]` | `log_level` | `INFO` | `DEBUG`, `INFO`, `WARNING`, `ERROR` |
| `[logging]` | `log_file` | — | Log file path with rotation |
| `[metrics]` | `health_port` | — | HTTP port for `/metrics`, `/health` |
| `[advanced]` | `sop_index_db` | `:memory:` | SQLite path for SOP index (C-MOVE persistence) |
| `[advanced]` | `sop_registry` | `sop_classes.yaml` | Path to SOP class YAML registry. 48 classes with this file vs 11 built-in without it. |
| `[advanced]` | `max_store_mb` | `0` | Max C-STORE dataset size in MB (0 = unlimited) |
| `[advanced]` | `http_timeout` | `30` | HTTP timeout for STOW/QIDO/WADO-RS (seconds) |
| `[advanced]` | `printers_yaml` | `printers.yaml` | Path to printer registry YAML (C-PRINT) |
| `[advanced]` | `stow_queue_max_mb` | `0` | Max RAM for STOW queue in MB. `0` = auto (15% RAM). |
| `[advanced]` | `stow_workers` | `0` | Background STOW-RS workers. `0` = auto (cpu_count/2). |
| `[advanced]` | `stow_queue_size` | `5000` | Max pending requests (slots). Prefer `stow_queue_max_mb` for byte-based sizing. |
| `[advanced]` | `health_check_interval_sec` | `5.0` | Health check ping interval in seconds |
| `[advanced]` | `health_dead_threshold_sec` | `30.0` | Seconds until server declared DEAD |

### CLI flags (override config values)

> All settings belong in `clarus-bridge.conf`. CLI flags exist for debugging/override only.
> For production, set `peer` in `[dimse]` section as comma-separated list.

| Flag | Description |
|:---|:---|
| `--config <path>` | Path to config file (default: `./clarus-bridge.conf`) |
| `--peer AE:HOST:PORT` | Register peer for C-MOVE (repeatable). **Prefer `[dimse] peer` in config.** |
| `--version` | Print version and exit |

## C-MOVE: How Move Destinations Are Resolved

C-MOVE needs to know **where** to forward instances. Bridge uses two complementary mechanisms:

| # | Mechanism | How it works | Use case |
|:---:|:---|:---|:---|
| 1 | **Auto-registration** | When a modality sends C-STORE, Bridge remembers its `AE:IP:port`. On subsequent C-MOVE with same AE as Move Destination → found automatically. | Modality sends images, then pulls them back. |
| 2 | **`--peer` (manual)** | Admin explicitly provides `AE:HOST:PORT` at startup. Always available, survives restarts. | Move Destination is a **different** machine (PACS archive, Weasis, another Bridge). |

**Resolution order:**

```
C-MOVE arrives with Move Destination = "WEASIS_SCP"
  → 1. Check manual peers (--peer)        ← higher priority
  → 2. Check auto-registered SCPs          ← fallback
  → 3. Return 0xA801 (Unknown Destination)
```

**Why `--peer` overrides auto-registration:** An auto-registered entry captures whatever IP the modality happened to use during C-STORE — which may be a NAT gateway, a temporary DHCP lease, or a different interface. `--peer` gives the admin explicit control: *"I know WEASIS_SCP lives at 192.168.1.5:11113, always use that."*

**Common patterns:**

```bash
# Single PACS archive as Move Destination
python clarus-bridge.py --peer PACS_ARCHIVE:10.0.0.1:104

# Test setup: sender and receiver are different processes on localhost
python clarus-bridge.py --peer WEASIS_SCP:127.0.0.1:11113

# Production: multiple peer PACS systems
python clarus-bridge.py \
  --peer NEURO_PACS:10.0.1.5:104 \
  --peer RAD_PACS:10.0.2.5:104 \
  --peer ARCHIVE:10.0.3.5:104
```

## SOP Class Registry (`sop_classes.yaml`)

**What is a SOP Class?** In DICOM, every image type has a unique identifier called a *SOP Class UID*. CT images are `1.2.840.10008.5.1.4.1.1.2`, MR images are `1.2.840.10008.5.1.4.1.1.4`, and so on. The Bridge needs to know which image types to accept via C-STORE.

**Why YAML?** Instead of hardcoding SOP classes in Python, the Bridge reads them from `sop_classes.yaml` at startup. To add support for a new modality (XA, RF, PT, NM, etc.), add one entry (3 lines) to the YAML file and restart the Bridge — no code changes needed.

**Schema:**

```yaml
sop_classes:
  "1.2.840.10008.5.1.4.1.1.2":       # SOP Class UID
    name: CT Image Storage            # human-readable name
    modality: CT                      # NEMA PS3.3 two-letter modality code
    accept: true                      # true = accept, false = reject with 0xA801
```

**Default registry** ships with 48 SOP classes: 45 active (CT, MR, CR, DX, MG, US, SC, NM, PT, XA, RF, VL, OP, RT*, IO) + 3 legacy retired classes still in active use on pre-2006 equipment. The built-in fallback (when YAML is missing) covers 11 SOP classes (8 active + 3 retired) — enough for basic CT/MR/CR/DX/MG/US/SC workhorse workflows. For custom modalities, edit the file or pass `--sop-registry /path/to/custom.yaml`.

**Graceful rejection:** Unknown SOP classes get status `0xA801` (SOP Class Not Supported) instead of a generic error. The modality can then decide whether to retry or skip.

## Integration Example

Connect a legacy modality through Bridge to Clarus Server on the same machine:

```bash
# Terminal 1: Clarus Server (with clarus.conf)
cat > clarus.conf << 'EOF'
[server]
host = 0.0.0.0
port = 8024
[auth]
no_auth = true
[storage]
db_path = ./clarus.db
storage_dir = ./data
[logging]
log_level = info
EOF
./clarus-server

# Terminal 2: Bridge (with persistent C-MOVE index)
python clarus-bridge.py --config /etc/clarus-bridge.conf
```

Modality configuration: set DICOM server to `CLBRIDGE@your-host:8104`.

For C-MOVE support (Bridge retrieves from Clarus and forwards to the modality), set `sop_index_db = /var/lib/clarus/bridge-index.db` in the `[advanced]` section of `clarus-bridge.conf` for persistent SOP tracking across restarts.

## Limitations

- C-PRINT — OK Generic DICOM Print driver (PS3.4 §H) works with any standard printer. Vendor-specific drivers (Fujifilm, Carestream, Agfa, Konica Minolta) need community diagnostic dumps — see **[Community Help Wanted!](../README.md#c-print-film-printing)**
- C-MOVE by series/instance — study-level only
- Requires Python 3.12+ and ~30 MB of RAM
- Bridge does not store DICOM files locally — all data lives in Clarus Server

For full limitations, production deployment (systemd), DIMSE status codes, and
troubleshooting, see the [Bridge documentation](../docs/bridge.md).

## Why Python, Not Rust

A natural question: Clarus Core is Rust, so why is Bridge in Python?

**The short answer:** DIMSE is a 30-year-old protocol with 30 years of
vendor-specific quirks. The only library that handles them all reliably
is `pynetdicom`. Rewriting that knowledge in Rust today would mean
repeating 15 years of real-world bug fixes — for a protocol the industry
is actively migrating away from.

### pynetdicom vs the Rust DICOM ecosystem

| | `pynetdicom` (Python) | Rust DICOM crates |
|---|---|---|
| **Age** | 15+ years of production use | ~2019, maintainer turnover |
| **DIMSE coverage** | C-STORE, C-FIND, C-MOVE, C-ECHO, C-GET, N-ACTION — complete PS3.7 | Experimental, incomplete |
| **SCP + SCU** | Both, production-grade | Basic SCU only |
| **Edge cases** | Tens of thousands of bug reports from real modalities worldwide | Not battle-tested |

### What "battle-tested" actually means

DIMSE is a standard on paper. In reality, every vendor interpreted it
differently. `pynetdicom` knows about these because someone, somewhere,
already hit the bug, filed it, and it got fixed:

| Vendor | Quirk | Bridge just works because… |
|---|---|---|
| **Siemens Definition AS (2008)** | Sends C-STORE with a non-standard Presentation Context that violates PS3.7 negotiation | pynetdicom's `AE.on_c_store` has a fallback path for this exact Siemens bug |
| **GE Revolution (2015)** | Violates C-MOVE response timing — sends status 0xFF00 (Pending) after a 30-second gap instead of the standard 5-second keep-alive | pynetdicom extends the DIMSE timeout when the association is still open |
| **Mindray (Chinese ultrasound, various)** | Sends PatientName in cp1251 inside (0008,0005) without declaring SpecificCharacterSet — the tag literally contains `ÈÀÂÍÎÂ` | Bridge auto-detects cp1251 byte patterns and converts to UTF-8 before forwarding to Core |
| **Toshiba Aquilion (2006)** | Sends C-STORE with Implicit VR Little Endian but incorrectly sets the Transfer Syntax UID to Explicit VR in the Presentation Context | pynetdicom falls back to the actual byte stream encoding, ignoring the declared UID |

These are not hypothetical. They are real bugs that hit real PACS
installations. Each one cost someone days of debugging before `pynetdicom`
was patched. A Rust rewrite starts from zero on every single one of them.

### When a Rust Bridge would make sense

- When `dicom-rs` reaches `pynetdicom`-level maturity (years, not months)
- When a paying customer needs 1000+ C-MOVE/hour and Python becomes the bottleneck
- When Bridge becomes a hard dependency for a regulated product (not the case — Bridge is optional)

Until then: **Python is not a compromise. It's the right tool for this job.**
The pragmatic choice is to spend engineering time on Clarus Station, S3 Tiering,
and certification — not on re-implementing 30-year-old DIMSE quirks in Rust.
