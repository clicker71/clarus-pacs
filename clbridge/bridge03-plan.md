## 0. Критический анализ ТЗ

### Сильные стороны

| Аспект | Оценка |
|:---|:---|
| **Структура документа** | ✅ Профессионально — 9 разделов, ГОСТ-стиль |
| **DIMSE-матрица** | ✅ Каждый неподдерживаемый протокол имеет конкретный статус-код |
| **C-FIND: ограничения** | ✅ 50 ответов, 30s timeout, 10 сессий — разумные защитные лимиты |
| **Кириллица** | ✅ Правильный выбор ISO_IR 144 (не UTF-8) для совместимости со старыми модальностями |
| **Границы версии** | ✅ Чёткий список «НЕ входит» |
| **Алгоритм C-FIND** | ✅ Пошаговый псевдокод, прослеживается каждый статус-код |
| **Тестовый план** | ✅ 27 unit + 9 integration + 4 load — внушительно |

### Слабые стороны

| # | Проблема | Серьёзность | Рекомендация |
|:---:|:---|:---:|:---|
| **1** | **Scope creep 10×** | 🔴 CRITICAL | Bridge v0.1 = 80 строк. ТЗ описывает ~800 строк + 27 тестов. Это не v0.3, это v1.0. |
| **2** | **YAML-конфиг + env override** | 🟡 HIGH | 200+ строк парсинга конфига для утилиты, которая сейчас принимает 7 CLI-параметров. Избыточно. |
| **3** | **Prometheus /metrics + /health** | 🟡 HIGH | Дублирует Clarus Server. Bridge — тонкая прослойка, не самостоятельный сервис. |
| **4** | **Интеграционные тесты на реальном железе** | 🟡 HIGH | Siemens 2008, GE 2010, Philips 2006 — у нас нет этого оборудования. Пункт невыполним. |
| **5** | **DVTK-валидация** | 🟡 HIGH | DICOM Validation Toolkit — отдельный продукт, сложная настройка. Не для v0.3. |
| **6** | **27 юнит-тестов на ~300 строк кода** | 🟡 HIGH | Соотношение тестов к коду 1:10 — перевёрнуто. Разумно: 8–10 тестов на критические пути. |
| **7** | **Нет миграции с v0.1 CLI** | 🟡 MEDIUM | ТЗ вводит `bridge.yaml`, но не объясняет судьбу `--host`, `--port`, `--user`, `--pass`. |
| **8** | **C-FIND 50 ответов — мало** | 🟡 MEDIUM | Рабочий список модальности может содержать 100+ пациентов. 50 — узкое место. |
| **9** | **Нет MoSCoW-приоритизации** | 🟡 MEDIUM | Всё «must have». Нет деления на MUST/SHOULD/COULD. |
| **10** | **ТЗ читается как v1.0 product spec** | 🟡 MEDIUM | 40+ страниц для v0.3 моста из 80 строк — перегруз документацией. |

### Вердикт

**ТЗ — добротное, но перегруженное.** Содержит v1.0-scope под видом v0.3. Требуется разделение на 3 спринта с приоритизацией по методологии MoSCoW.

## 2. Разбивка на спринты

### Спринт 1: C-FIND Core + DIMSE (Неделя 1)

**Цель:** C-FIND работает, неподдерживаемые команды отклоняются корректно.

> **Thinking Effort:** `High` — pynetdicom C-FIND SCP, DIMSE-статусы.

| ID | Тип | Название | AI-режим | Описание |
|----|-----|---------|---------|----------|
| BRG-001 | Spike | **Архитектор: pynetdicom C-FIND SCP handler** | Pro (Max) | Проанализировать pynetdicom `AE.on_c_find`, формат Dataset ответа, статус-коды. Спроектировать C-FIND → QIDO-RS маппинг. |
| BRG-002 | Story | **Писатель: C-FIND SCP (Patient Root)** | Pro (High) | Реализовать `handle_c_find()`. Принять Dataset, извлечь PatientID/AccessionNumber, вызвать QIDO-RS, вернуть C-FIND-RSP с данными. |
| BRG-003 | Story | **Писатель: DIMSE-отказы** | Flash (None) | C-MOVE → C002, C-GET → C002, C-PRINT → C602. Пустой Dataset в ответе. Логирование. |
| BRG-004 | Task | **Верификатор: C-FIND тесты** | Flash (None) | 5 тестов: PatientID (1 результат), AccessionNumber (3 результата), пустой ключ (A900), Study Root (A600), C-MOVE отказ (C002). |

### Definition of Done (Sprint 1)

- [ ] `python clarus-bridge.py` принимает C-FIND от `findscu`
- [ ] PatientID → QIDO-RS → 1 C-FIND-RSP с PatientName/StudyDate/Modality
- [ ] AccessionNumber → QIDO-RS → N C-FIND-RSP
- [ ] Пустой ключ → A900
- [ ] Study Root → A600
- [ ] C-MOVE → C002
- [ ] C-GET → C002
- [ ] C-PRINT → C602
- [ ] C-ECHO и C-STORE работают без регрессий
- [ ] `findscu` + `movescu` + `getscu` — ручная проверка

### Спринт 2: Кириллица + Защитные лимиты (Неделя 2)

**Цель:** Кириллический PatientName без искажений, мост не падает при перегрузке.

> **Thinking Effort:** `High` — ISO_IR 144 кодирование, многопоточные лимиты.

| ID | Тип | Название | AI-режим | Описание |
|----|-----|---------|---------|----------|
| BRG-005 | Spike | **Архитектор: ISO_IR 144 в pynetdicom Dataset** | Pro (Max) | Как pynetdicom кодирует SpecificCharacterSet. Формат ответа с (0008,0005)="ISO_IR 144". |
| BRG-006 | Story | **Писатель: автоопределение кириллицы** | Pro (High) | Проверить PatientName/StudyDescription на U+0400–U+04FF. Если да → (0008,0005)="ISO_IR 144", упаковать в ISO 8859-5. Если нет → Latin-1 без (0008,0005). |
| BRG-007 | Story | **Писатель: C-FIND лимиты** | Pro (High) | max_responses=50, session_timeout=30s, max_concurrent=10. При превышении → B000/A700. |
| BRG-008 | Story | **Писатель: graceful degradation** | Pro (High) | Clarus недоступен → A700 (не падать). HTTP 500 → A700. Таймаут → A700. |
| BRG-009 | Task | **Верификатор: кириллица + лимиты** | Flash (None) | 4 теста: кириллический PatientName, латинский без (0008,0005), >50 результатов → B000, Clarus down → A700. |
| BRG-010 | Task | **Верификатор: регрессия v0.1** | Flash (None) | C-ECHO + C-STORE через bridge → Clarus (как в PAX-021b). |

### Definition of Done (Sprint 2)

- [ ] Кириллический PatientName в C-FIND-RSP: «Иванов^Иван» без искажений
- [ ] Латинский PatientName: без тега (0008,0005)
- [ ] 51 результат → B000 + ровно 50 ответов
- [ ] Clarus выключен → C-FIND возвращает A700, мост продолжает работать
- [ ] 11-я C-FIND-сессия → A700
- [ ] C-ECHO + C-STORE без регрессий
